- (constraint) [ADOPTED] Tech stack fixed by PRD: .NET Core backend, Angular frontend — not open for reconsideration.
- (constraint) [ADOPTED] Zero-cost budget: free-tier or local hosting only, no paid infra.
- (constraint) [ADOPTED] Weekend-scale build window — load-bearing timeline, not soft target.
- (constraint) [ADOPTED] Responsive web only (FR-10), no native app track, mobile and desktop equal priority.
- (constraint) [ADOPTED] Single user (the founder), no login wall (FR-9) — trust boundary is device access, not an auth gate. Financial data still encrypted at rest.
- (constraint) [ADOPTED] Totals (FR-7, FR-8) must be exact — no estimation or rounding; money arithmetic cannot use floating point.
- (constraint) [ADOPTED] No offline/PWA support, no analytics/telemetry infrastructure in v1.
- (decision) v1 runs on the same machine/network only — no internet-facing deployment. Prevents: building auth-over-internet or public-hosting concerns nobody asked for. Rule: app binds to local network only; no public ingress, no TLS-facing-internet cert story.
- (decision) [ADOPTED] SQLite as single-file embedded DB. Binds: all persistence. Prevents: standing up/operating a DB server for a single user. Rule: no DB server process; storage is one file, backed up by copying it.
- (version) SQLite via EF Core Sqlite provider (verify current EF Core version against .NET target during build).
- (version) [ADOPTED] .NET 10 (current LTS, released Nov 2025, supported to Nov 2028) — confirmed via web search 2026-07-03.
- (version) Angular 22 (current stable, released Jun 2026, active support to Dec 2026 / LTS to May 2028) — confirmed via web search 2026-07-03.
- (decision) Backend paradigm: Minimal APIs, feature-grouped, endpoints call EF Core DbContext directly — no Repository/Service layer. Binds: all backend endpoints. Prevents: ceremony (interface+class per entity) with no second-implementation payoff at this scale; divergent teams building inconsistent service/repo abstractions. Rule: no Repository or Service interface layer between endpoint and DbContext; group endpoint files by feature (e.g. Entries/, Categories/), not by technical layer (no Controllers/ Services/ Repositories/ folders).
- (decision) Server computes, client displays: every add/edit/delete mutation returns the fresh authoritative total(s) from the server; client never independently re-derives a total. Binds: FR-7 (running total), FR-8 (monthly breakdown). Prevents: client-side floating-point summation drifting from the server's exact number. Rule: money is decimal (C#) end-to-end, never float/double; client renders server-supplied totals only, no client-side summation of amounts for display.
- (decision) [OVERRIDE] Categories are a DB table, not a hardcoded enum, and v1 enables user-created custom categories (free-text, auto-created on first use per the existing prototype's isNewCategory pattern). Binds: FR-2, category storage/creation. Prevents: two builders diverging on whether categories are fixed or open. Rule: Category entity has id + name (+ isPreset flag to distinguish the seeded Food/Transport/Shopping/Other from user-added ones); entry-creation accepts an existing category id OR a new category name, case-insensitive-deduplicated against all known names before creating a new one.
- (question) This decision contradicts PRD FR-2 ("fixed set... no free text... no catch-all") and the Out-of-Scope list's "category management (add/edit/remove/reorder categories)" exclusion. User chose to enable category creation in v1 anyway. Flag to reconcile the PRD (amend FR-2 / Out-of-Scope) before/alongside finalizing this spine, so PRD and architecture don't silently diverge.
- (decision) Single ASP.NET Core process serves both the API and the built Angular static assets (wwwroot) on one port. Binds: deployment topology. Prevents: needing CORS config, two processes to start, or two ports to open on the LAN. Rule: Angular production build output is published into the .NET app's wwwroot; one process, one port, one thing to run.
- (decision) [ADOPTED] Frontend state: Angular signals + plain injectable services calling the API, no external state library (no NgRx). Binds: all frontend state. Prevents: actions/reducers/effects ceremony for what is one entries list + a derived total.
- (decision) Encryption-at-rest is satisfied by OS-level full-disk encryption on the trusted device (BitLocker/FileVault), not application-level DB encryption. Binds: NFR security/data-handling. Prevents: adding SQLCipher/key-management complexity that reopens the key-storage problem the no-auth-wall decision already sidesteps. Rule: no application-level encryption of the SQLite file; README/setup notes must tell the user to ensure disk encryption is enabled on the host machine.
- (decision) AD-2 corrected: totals are NOT returned on every entry mutation. Phase 4 UX (1.3-home) moved the running total off Home entirely — it lives only on the Monthly Breakdown page (2.1), computed via a separate month-summary query. Entry add/edit/delete responses return only the saved/changed entry; a toast confirms save on Home (no total shown there). Binds: FR-7, FR-8. Prevents: building a total-on-every-mutation contract the finalized UX doesn't use.
- (question) PRD FR-7 text ("running total is visible on Home") is now stale relative to finalized UX Phase 4 (1.3-home: "the running total was moved to the Monthly Breakdown page only, decided during 1.1 discussion"). This is a second PRD/downstream-doc divergence (alongside the categories one) that predates this architecture session. Flag to amend PRD FR-7 to match the finalized UX rather than the reverse — the UX is the more granular, already-validated source on this specific point.
- (decision) Added capability: month navigation. Monthly Breakdown (2.1) browses past months via prev/next, range bounded by earliest month with any recorded entry through current month (data-driven, no fixed lookback). Binds: FR-8. Rule: backend exposes a month-summary query parameterized by month (e.g. GET /api/months/{yyyy-MM}/summary) and the earliest-available-month bound is derived from MIN(Entry.CreatedAt), not configured.
- (decision) Added capability: category drill-down. Tapping a category bar on 2.1 opens a read-only, most-recent-first transaction list for that category+month (2.2), reusing the Overlay Drawer/Sheet design-system component (right-side drawer desktop, full-screen sheet mobile). Binds: FR-8. Rule: backend exposes entries filtered by month+category, sorted CreatedAt descending; this panel is read-only (no edit/delete) by explicit UX decision — corrections happen only on Home.
- (convention) Responsive breakpoint: single-tier, bp-mobile up to 639px / bp-desktop 640px+ (no tablet tier), per Design System. Binds: all responsive layout code and the Overlay Drawer(desktop)/Sheet(mobile) switch specifically. Implement via a single shared breakpoint constant/media query, not per-feature hardcoded widths.
- (decision) Shared UI component convention added: Overlay (modal/drawer/sheet) is used by both Home (1.2 confirm popup) and Breakdown (2.2 drill-down panel) — promoted to a shared, reusable Angular component per the Design System's own 2nd-use-promotes-to-Component rule. Binds: frontend structure. Rule: client/src/app/shared/ holds reusable UI components (Overlay, and any future 2nd-use pattern) in addition to API services/models — not services/models only.
- (convention) Async state contract: every feature service exposes Default/Loading/Error signal state for its data (matches the Default/Loading/Empty/Error page-state tables already specified per-page in the UX docs for Home, 2.1, and 2.2). Binds: all frontend feature services. Prevents: each feature inventing a different loading/error signal shape.
- (question) AD-4's 'same machine/LAN' scope is broader than the PRD's no-auth override, which is explicitly conditioned on a single trusted device and says to revisit if the deployment model moves off that (shared device, multi-tenant hosting). User explicitly chose same-machine/network in this session (any device on the home LAN can reach the app unauthenticated, not just one). Flag to amend the PRD's NFR text to acknowledge this broadened trust boundary, or narrow the architecture back to single-device-only if that widening wasn't intended.
- (question) Encryption-at-rest (AD-4) is discharged entirely via OS-level full-disk encryption, which is NOT verified or guaranteed enabled (e.g. BitLocker isn't on by default on non-Pro Windows editions) and has no in-app fallback. Flag as an open risk for the user to confirm/enable disk encryption on the actual host machine before treating the NFR as satisfied; not an architecture-level fix.
- (event) Reviewer Gate ran: lint (clean), rubric walker, version/reality-check, adversarial consistency attack. Findings applied below.
- (decision) AD-5 tagged [OVERRIDE]: contradicts PRD FR-8 ("no drill-down required") and Out-of-Scope ("charts/visualizations beyond plain sums"). Not arbitrary — reconcile-ux-scenarios.md (PRD-stage) already flagged Scenario 02's 'distrusting a number' fear as unaddressed and un-mitigated in the PRD; Phase 4 UX (2.1/2.2) resolved it by adding the bar chart + drill-down. Architecture follows the resolved UX. Flag to amend PRD FR-8/Out-of-Scope alongside FR-7 and categories.
- (decision) Hard delete only, no soft-delete flag. Binds: FR-6, Entry schema. Prevents: one builder adding IsDeleted while month-summary/drill-down/earliest-month queries (which another builder writes) never filter it, silently double-counting deleted entries. Rule: DELETE removes the row; no IsDeleted/soft-delete column anywhere in the schema.
- (decision) AD-3 tightened: category match-or-create is a single function owned by Categories/ (e.g. a static resolver method), called by the Entries endpoint on entry creation — not duplicated inline logic. Prevents: Capability Map assigning category creation to Categories/ while AD-3's rule text implied Entries owns the matching logic; two implementations of the same dedup rule.
- (convention) Entry API response shape pinned: every endpoint returning an Entry includes a nested category object ({id, name}), never a flat categoryName string or bare categoryId alone. Prevents: CRUD/list/drill-down endpoints each independently choosing a different shape, breaking a shared Angular model.
- (decision) CreatedAt is immutable: editing an entry (FR-6) changes Amount/CategoryId only, never CreatedAt. Binds: AD-5's month-bucketing and earliest-navigable-month floor (MIN(CreatedAt)), which silently breaks if edits could shift an entry's month. Rule: no endpoint accepts or updates CreatedAt after creation.
- (decision) Shared-component convention corrected: Overlay is decided as a shared component from day one (built once in client/src/app/shared/components/, used by both Home's confirm popup and Breakdown's drill-down panel from the start) — not something discovered/promoted organically on a '2nd use' two parallel builders might each think is their 1st.
- (decision) AD-2/AD-5 caveat: EF Core's SQLite provider cannot translate Sum/GroupBy over decimal (or reliably order by DateTimeOffset) to SQL. Month-summary and drill-down queries fetch the month's entries via a WHERE-filtered (month-bounded, small-volume) query, then sum/group/sort in-process using C# decimal (LINQ-to-Objects) — still exact, still never client-side, just not SQL-aggregated. Trivial cost at this data volume.
- (constraint) Error envelope wording softened: 'ProblemDetails-shaped JSON error envelope (RFC 9457 style)' rather than claiming strict RFC 9457 compliance, since ASP.NET Core's own explicit RFC 9457 support is still tracked/unmilestoned upstream.
- (constraint) Encryption caveat sharpened: distinguish Windows Home's conditional 'Device Encryption' (needs modern hardware, 24H2+) from true BitLocker (Pro/Enterprise) when the user verifies disk encryption on their host.
